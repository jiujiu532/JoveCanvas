# Render deployment

The root `render.yaml` creates a Web Service, a dedicated generation Worker, PostgreSQL, and a Web persistent disk. Web and Worker share a Render environment group with an auto-generated maintenance token. The Worker calls Web maintenance APIs only over Render’s private network and never opens a direct database connection.

[Deploy to Render](https://render.com/deploy?repo=https://github.com/jiujiu532/JoveCanvas)

## Steps

1. Connect the GitHub repository and create a Blueprint.
2. Set `NEXT_PUBLIC_SITE_URL` to the final Render hostname or custom HTTPS domain.
3. Confirm `VOZEB_PRO_ENCRYPTION_KEY` and the environment-group `VOZEB_PRO_MAINTENANCE_TOKEN` were generated by Render and will be retained long term.
4. Confirm Web mounts the `vozeb-pro-data` disk at `/app/web/.data` and that the Worker is running.
5. After deploy, open `/install` to create the first admin.
6. In admin, configure model channels and default logical models, then check that `/api/health/ready` succeeds and includes a valid Worker heartbeat.

## Instance and persistence boundaries

- Blueprint defaults: `starter` Web, `starter` Worker, `basic-256mb` PostgreSQL, 10GB disk (billable). Background Worker and disk cannot use free instances.
- Render’s ephemeral filesystem is not suitable for long-lived media; Blueprint unifies `VOZEB_PRO_DATA_DIR` with the disk at `/app/web/.data`.
- Liveness uses `/api/health/live` so first install can complete; readiness (`/api/health/ready`) is for external monitors (DB, encryption key, admin, Worker heartbeat).
- Canvas, assets, short drama, and workbench records live in PostgreSQL; media files must be backed up with the disk.
- Disk is mounted on Web only; Worker claims work via private maintenance APIs. Worker must not receive `DATABASE_URL`.
- Blueprint structure ≠ resources already provisioned. Before go-live, verify real costs, first deploy, restart recovery, payment webhooks, long tasks, and media generation.
